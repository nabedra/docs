---
title: "Request receipts"
description: "Submit without waiting for completion, observe terminal results, and recover receipts by run and request ID."
---

Use `Database.submit()` to queue an [operation](/reference/database-http#operation-payloads)
and get a receipt without waiting for completion. The returned `queued` state
confirms acceptance. Poll the receipt for the result. Ordinary table and query
methods wait for completion.

Follow the [quickstart](/guides/quickstart) to install the client and start a
server. Run the example in that Python environment with `NABEDRA_TOKEN` set.
Use the server's URL and include `database=` if it requires a database selector.
The example lists tables without changing data.

```python
from uuid import uuid4

from nabedra import Database

client = Database(url="http://127.0.0.1:8000")
request_id = str(uuid4())
operation, payload = "table.list", {}
print("Request ID:", request_id)
receipt = client.submit(operation, payload, request_id=request_id)
run_id = receipt.run_id
print("Run ID:", run_id)
print("Accepted:", receipt.state)

terminal = receipt.wait(timeout=30)
assert terminal.state == "succeeded", terminal.error
print(terminal.result)
```

The example prints the two IDs, `Accepted: queued`, and a list of table
descriptors. An empty database returns `[]`.

## Receipt fields and states

`RequestReceipt` exposes `request_id`, `run_id`, `state`, `result`, and `error`.
Its `terminal` property is true for `succeeded`, `failed`, or `abandoned`.
The other states are `queued`, `running`, `committing`, and `reconciling`.
`poll()` returns a fresh receipt. `wait()` returns a terminal receipt even if
the operation failed. Inspect `result` on success and `error` on failure. A
wait timeout raises `TransportError` and stops client polling. You can resume
polling the same receipt.

## Recovery and retention

Before sending a write that you may need to recover, save its request ID,
operation name, and exact payload, including JSON field order. Save the run ID
when you receive it. When you reconnect, use an API for the same database with
the same credentials and selector.

- **Run ID and request ID.** Poll with `client.receipt(run_id, request_id)`.
- **Request ID only.** If the acceptance response was lost and the same worker
  run is still active, repeat `client.submit(operation, payload, request_id=request_id)`
  with the original body. This attaches to the existing request if the server
  accepted it, or submits it for the first time if the original never arrived.
  A changed body for an existing UUID raises `ConflictError`.
  If you cannot confirm the run is still active,
  [reconcile the write](/python/errors#resolve-an-uncertain-write) before submitting it again.

Read results live in worker memory and can expire or hit the [retention byte
limit](/server/worker-runtime#configuration-files). Polling for an expired
result in the same run raises `NotFoundError`.
Accepted work can survive an API restart or a worker loss while a complete
queue copy survives. A cold start after every worker stops begins a new run and
abandons outstanding work. Durable mutation decisions can still resolve old
receipts. If an old receipt is `abandoned` or polling raises
`UnknownOutcomeError`, [reconcile the write](/python/errors#resolve-an-uncertain-write)
before submitting it again. See [queue recovery](/server/worker-runtime#admission-and-recovery).
