Start with [standalone OLTP](/server/oltp) for local use. The distributed runtime and provider adapters in the source checkout are experimental. Use the [OLTP acceptance contract](/contributing/oltp-contract) and the recorded evidence for your topology before relying on failover or automatic storage growth.

## Process roles

| Role | Native entry point | Responsibilities |
| --- | --- | --- |
| Standalone | `nabedra-db serve --data-dir PATH` | Run a single local owner, public API and in-memory queue against one data directory. |
| API | `nabedra-db api --config PATH` | Start the supervised public listener and route work to an authorized worker runtime. |
| Registered worker | `nabedra-db worker --bootstrap PATH` | Open registered local storage and an authenticated queue endpoint. |
| Provisioned data worker | `nabedra-db data-worker --bootstrap PATH` | Enroll a provisioned worker, advertise pools and run its queue and data services. |

Use POSIX process descriptors for the supervised entry points. The OLTP API expects an OLTP configuration and requires supervisor startup. Bootstrap documents contain authority identities, endpoint or pool bindings and paths to protected credentials. Generate inputs for the intended topology. OLAP configuration files describe a different deployment.

The typed Raft groups split Control, timestamp allocation, request status, catalog, and data responsibilities. Data groups use eligible mounted pools. Placement, replacement and removal require authenticated ownership and current identities, and drains must preserve quorum and request ownership. Capacity becomes usable only after the database validates the worker and its mounted pools.

## Configuration boundaries

| File | Contents |
| --- | --- |
| API configuration | Schema `version`, `engine: "oltp"`, bind address, database selector, protected `auth_file`, and `topology`. A local topology uses `mode: "local"` and `data_dir`. A remote topology uses `mode: "remote"` and the registered remote authority configuration. |
| Registered worker bootstrap | Version 1, worker bind address, protected `auth_file`, registered `node` configuration, `resources`, and `execution`. The automatic split policy requires a mounted pool. |
| Provisioned worker bootstrap | Versioned worker and resource settings, a `node` with the exact worker intent, control placement and enrollment identities, and paths to the worker certificate, private key, and authority CA. |

Keep each process's protected auth and TLS material readable only by its intended service account. Size `execution` and `resources` together using the [worker configuration reference](/server/worker-runtime#configuration-files). Start from the configuration generated by the intended [acceptance fixture](/contributing/oltp-acceptance) when testing a distributed topology.

## Provider integrations

The Python `nabedra.deployment` package includes Docker, EC2 and EKS adapters, EBS mount observation, a growth controller, and optional EKS replacement verification. Install the checkout with `[aws]` or `[eks-replacement]` in an operator environment when that path requires them.

Provider observations report instances, Pods and volumes. The database decides which pools count as mounted capacity, which workers may vote, and when removal is authorized. The automatic growth planner folds published inventory and uses idempotent claims for lifecycle commands. The `growth-plan` native command reads inventory and emits a plan without applying provider changes.

OLTP operator operations use the protected worker administration endpoint when configured. They include `storage.index.*` for index lifecycle, `storage.shard.split` for placement growth, and worker drain/replacement operations. The public data bearer cannot call these operations. `Table` and `Query` retain the shared ORM API.
