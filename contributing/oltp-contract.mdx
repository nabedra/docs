title: "OLTP test contract"
description: "Read the essential correctness, durability, deployment, and scaling requirements for OLTP."
---

These acceptance cases define the proposed OLTP engine in [the implementation plan](https://github.com/nabedra/database/blob/1418bad88e1df1b8c868b88889a120e37059c1c0/plans/oltp-engine.md). They are future assertions, not executed results. Retain the [scheduler contract](/contributing/scheduler-contract), including its named regressions and evidence rules. The existing OLAP S3/catalog cases remain required for that engine. The user's 2026-11-16 requirement removes fixed logical-table row/byte caps from the initial OLTP design; storage growth must add shards, volumes and workers without changing application calls.

Use deterministic barriers, a controllable timestamp allocator, a serial operation oracle, seeded faults, and real API/worker processes. Inject faults before and after disk sync, quorum acknowledgment, transaction decision, intent resolution, and receipt replication. A successful HTTP response alone does not establish atomicity, durability, or failure recovery. Process-kill evidence alone does not establish power-loss/fsync correctness.

| ID | Scenario | Required assertions |
| --- | --- | --- |
| O01 | Execute the same unchanged Python program and all thirteen operations against both engines | Same descriptors, results, types, ordering, operation errors, table identities, authentication and database scope. Keep advisory `mode` and legacy `format="parquet"` behavior. The matching ORM handles large counts from the initial OLTP milestone with unchanged calls; document old client decoder constraints without imposing them on server storage. Whole-table limit removal is an intentional change covered by O21. |
| O02 | Build/package OLAP, OLAP without S3, OLTP without S3, and OLTP with S3 backup; try both engines and neither | Valid builds have exactly the intended dependencies and engine. Both/neither fail compilation. OLTP starts without S3/catalog credentials, and enrollment/manifests reject mixed engines or disk formats. Installed binary reports its engine. |
| O03 | Primary-key hits/misses, ranges, typed codecs, stale routes and table handles | A point lookup executes on one owning data shard, with no table scan or Parquet decode. Admission replication is measured separately. Test integer extrema, negative values, string boundaries, float signed zero, tombstones and invalid/nonfinite values. Stale epochs redirect/fail without partial results. |
| O04 | Compare indexed/scan/distributed query results to the pure evaluator | Exact predicate logic, residual filters, default key order, descending ties with ascending key, projection, top-k, count-with-limit, empty results, and bounded-body/result errors. Include `or`/`not`, duplicate index values and updates/deletes. |
| O05 | Saturate caches/native buffers and overlap scan, compaction, flush, snapshot transfer and index build | Aggregate native threads and memory remain within declared budgets, including pinned blocks and page cache measurement. Bound scan pollution, merge memory, I/O queues and disk growth. Inject allocation failures and verify unrelated work progresses. |
| O06 | Lose quorum, delay/fsync-fail a voter, corrupt a log/checkpoint and re-elect leaders | No durable acknowledgment precedes required stable storage. Read/write authority requires the right quorum and applied state. Reject corrupt/foreign replicas. Preserve every acknowledged mutation under the stated one-AZ failure model; never fabricate availability without quorum. |
| O07 | Single- and multi-shard batches with a failure at every prepare/decision/apply boundary | Before COMMIT, rows/indexes are private. After COMMIT, every successful snapshot read includes all relevant changes or none according to its timestamp, even when one participant has not finalized. No second decision or mutation application. Prove cross-shard duplicate-key conflicts abort the whole batch. |
| O08 | Concurrent same-key mutations, overlapping batches, uniqueness/absence checks, create/drop and pool-space reservation races | Histories admit the specified serial order. No lost updates, invalid uniqueness, storage reservation overshoot, stale schema write, deadlock or unbounded retry. No-op and conflict results remain stable by identity. Mutations that retry recompute from the required fresh snapshot without creating another logical request. |
| O09 | Timestamp allocation overlaps prepare, scans, allocator failover, old leader resume and clock jumps | Timestamp monotonicity and real-time constraints hold. Commit timestamps follow all participant prepares. Reads resolve ambiguous older intents for missing/base/index keys and cannot miss a committed insert. Cached/batched timestamps must not appear behind previously completed operations. |
| O10 | Kill coordinator after COMMIT, delay decision responses, retry resolutions and lose terminal replication | Any authorized survivor recovers the same decision and exact result using the original identity/digest. Status-group uncertainty never becomes a locally invented ABORT or COMMIT. Receipt-race handling preserves immutable terminal records and accepted authorization snapshots. |
| O11 | Crash between Raft log sync, state batch write, applied-position update, checkpoint and log truncation | Recovery replays only the committed state that is required, with data/index/result/applied-position agreement. Repeated application is idempotent. Torn/truncated/corrupt state fails explicitly. A proposed 1PC or local/follower-read optimization must pass these and O07/O09 under its exact durability settings. |
| O12 | Pause/fail online index build during backfill, change replay, validation and epoch publication | Queries never choose an incomplete index. Committed writes during the build are present exactly once. Recovered/restarted builds and retired index versions retain the correct snapshot behavior without unbounded RAM/disk. |
| O13 | Saturate CPU, queue bytes/counts, retention and disk headroom while submitting valid work | Reuse Q01-Q06/M01-M03/F01-F03 assertions. Every accepted identity remains represented until terminal; overload before acceptance is explicit. Disk reserves still allow consensus/ABORT/COMMIT/settlement. No reservation leaks or invented successes after result expiry. |
| O14 | Lose APIs/workers sequentially; retain one complete queue copy; then restore capacity | Same-run recovery retains request bytes, pinned read timestamp and schema, identity, original authorization and outcomes. Data/status quorum loss can block progress but cannot drop the queue or start a new run. Include queue-bootstrap empty/single/page regressions and signed control saturation. |
| O15 | Stop all workers with queued, prepared and ambiguously committed operations; cold-start on retained disks | New run has no pending old application requests. Honor decisions ordered before the new group-local fence, reject old decisions after it, and abort remaining preparations without re-executing user logic. Old receipts distinguish committed, abandoned and unavailable proof. Include allocator/status/shard fence interruption. |
| O16 | Split, move and restart shards during scans, commits and queue takeover; interrupt snapshot installation | Preserve key coverage without overlaps/gaps, MVCC pins, index consistency, transaction/dedup history and lineage. Old routes cannot publish; new generation plus applied position activates atomically. Unrelated shards in shared storage remain intact. |
| O17 | Scale up/down with learners behind, low disk, active transactions, provider failure and a last queue holder | Never remove a required voter or queue copy before replacement/copy evidence. Promote after verified catch-up; drain before terminate. Keep minimum AZ placement and replica count. Missing adapter rejects autoscaling as A01 requires. |
| O18 | Exercise actual EC2/EBS/EKS storage lifecycles, AZ loss and Pod/worker identity replacement | Check same-AZ volume binding, one writer, retained PVC/data, encryption/permissions, native sync behavior, mTLS, UID/incarnation matching and quorum-aware drain. A Pod deletion acknowledgment or HTTP fake does not establish volume detach/fencing or instance termination. |
| O19 | Backup at a transaction boundary, archive changes, restore base/PITR after loss of all live copies | Checksums/schema/map/transaction cut agree; include every participant of committed transactions through the target and exclude uncommitted/abandoned work. Queue starts empty. Declare measured archive RPO, restore time and missing-archive behavior. Drill unavailable keys, truncated exports and failed manifest publication. |
| O20 | Offline migrate a pinned OLAP database to empty OLTP storage and switch endpoints | Schema, table UUIDs, deterministic rows/order and per-range hashes match. Writes stay stopped during the cut. Partial imports stay unavailable; source rollback data remains. Mixed-engine files and nonempty targets fail safely. No source queue replay in the target. |
| O21 | Grow one table past 100,000 rows and 64 MiB across shard splits and volumes, with concurrent reads/mutations and restarts | The 100,001st row and later batches succeed with capacity available; exact count/get/query semantics survive growth. No table row/byte/shard quota, serialized global quota counter, or whole-table decoded buffer remains in OLTP. Preserve bounded requests/results/tasks, checked counts, and exact query limits. Crossing a shard target triggers a safe split under the same table ID. Missing capacity yields an explicit resource outcome, never a logical table-size error. |
| O22 | Mix shard-local reads, broad queries, reductions and dependent transactions on unequal workers | Apply C01-C07/F01-F03/U01-U03 to eligible data owners. Enforce query worker caps, fairness and resource conservation. Waiting for child/status/consensus work holds no compute permit. Reserved control/lock-resolution work progresses under saturation. |
| O23 | Increase ready queue membership and churn it during read-heavy and I/O-heavy load | Prove all-ready replication before acceptance and retained request conservation. Measure per-request fan-out bytes, slowest-replica latency, scheduler occupancy and throughput. No silently substituted quorum/scoped queue or disabled receipt handling. |
| O24 | Execute warm/cold, indexed/unindexed, mixed-load and matched PostgreSQL benchmarks | Record B01/B02 environment and all declared repetitions/latency distributions. Match durability/isolation/hardware/client conditions, include errors/rejections and end-to-end ORM time, and preserve accepted-ID accounting. No library-only or relaxed-durability headline comparisons. |
| O25 | Add workers/replicas and repeat fixed-data/growing-data/hot-key/maintenance workloads | Report actual scaling, data moved, catch-up duration, cache changes, tail latency and cost. Separate read replicas from data shards. Include unchanged-key contention and per-AZ failures. Never infer a throughput multiplier or PostgreSQL speedup from worker count alone. |
| O26 | Add independent volumes to existing workers with large tables, then move/split shards across pools; fail or remove a mount | Keep table/shard identities, snapshots, atomic batches, replica failure domains and exact counts. Pool addition changes available storage without adding compute threads or queue replicas. Verify worker/pool/provider/filesystem identity and exclusive ownership before opening; never write into an absent mount's root-disk directory or reformat a reused disk. Cache/native-thread/memory budgets remain aggregate across pools. Drain a pool before detach. |
| O27 | Expand a volume/PVC, attach another, and exhaust host attachment or I/O headroom while injecting provisioning failures/lost replies | Growth is idempotent and advertised only after actual filesystem/pool readiness. On EKS, distinct-PVC additions use a controlled worker replacement while other queue holders and shard quorums survive. Host limits cause eligible placement on new workers; enforce cross-AZ replica capacity before writing. Failed/unauthorized growth does not lose accepted work or fabricate capacity, and no adapter remains A01. |
| O28 | Grow a table's routing/index/backup metadata beyond one catalog/control-message limit while splitting, taking snapshots and restarting scans | Paged metadata covers every range exactly once at the pinned epoch with bounded caches and authenticated continuations. No fixed manifest-byte or shard-count table ceiling appears. Interrupt/retry pagination without missing or duplicate rows, lost snapshot pins or stale-route publication. Exercise count aggregation beyond previous decoder limits and checked arithmetic without loading the entire table or routing map. |

## Additional recovery regressions

| ID | Scenario | Required assertions |
| --- | --- | --- |
| O29 | A native write returns an ambiguous error after WAL persistence but before the corresponding live decision is visible; retry through the same and another pool handle | Absence from the live view cannot authorize recomputation, a regenerated table UUID, another logical decision, or a successful strong read from uncertain state. Every alias of that physical pool shares its recovery-required state. An already authoritative exact decision remains reconcilable. Reopen through storage recovery before resuming execution; replay committed state, never a pending application request. Unrelated healthy pools remain usable. Label deterministic fault-model evidence separately from actual native fsync/power-loss injection. |

O22/C07 writer-wait regression: hold only the engine's asynchronous writer ownership, submit two real mutations, and wait until both are blocked on that ownership. Neither may own a scheduler CPU grant or a native execution slot needed by an unrelated read. Complete an exact read and authorized receipt before releasing the writer, then assert both mutations apply once and all temporary charges settle.

O05/F03 native-cancellation regression: pause a native operation after dispatch, abort the awaiting future, and assert its CPU/memory and native execution ownership remain charged while native work is still live. Release and join it, verify the exact durable result or explicit uncertainty, and assert every charge returns to baseline once.

O05/O11/F03 Raft-append cancellation regression: cancel an append awaiter both before native dispatch and during a gated native write. Its owned entries, write ordering and completion callback must survive until storage settles. Shutdown drain must include tasks waiting for writer ownership or native capacity, including tasks that do not yet own a native lease. A later append cannot overtake the cancelled caller's write. Check the exact callback result and release every retained charge once.

O04/M01 wide-key paging regression: scan multiple pages whose keys consume a substantial part of the declared scratch budget. Reuse bounded key storage and retain at most the required continuation key per page. The scan must make progress without accumulating one temporary key copy per visited row. Check exact ordered coverage and release scratch and native value ownership after each page.

O05/C07 consensus-progress regression: hold the Data scratch arena and every Query native executor slot. Control/TSO/Status log ownership, append and decode must still use their protected capacity. Small Data/Catalog consensus metadata operations, including vote and committed-position persistence, must also retain protected execution capacity. A Control reply buffer alone does not establish native progress. Keep large data entries separately bounded and check actual persistence and reads before releasing the held query resources.

O11/O16 snapshot-activation regression: corrupt the incoming header's applied position or membership relative to its staged body, and attempt stale activation during a state transition. Reject before changing the active generation. Existing rows, unrelated group keys and the prior snapshot remain intact. Check under the same ownership boundary that commits activation.

O10/O29 unreadable-proof regression: commit an identified mutation, then make its stored decision encoding or namespace unreadable. Lookup and same-identity replay must report an unknown outcome, without changing the write sequence, recomputing the operation or generating another table UUID. Keep ordinary pre-publication validation certainty separate. Label corrupted-encoding models separately from actual native storage fault injection.

O09/Q06 snapshot-pin regression: race snapshot allocation with garbage collection. Timestamp allocation and pin insertion must be one durable transition, and retries must recover the same pin. A reserved timestamp watermark cannot authorize deleting a version still needed by a surviving request. Release requires matching terminal-copy evidence or an explicitly authorized abandonment path.

O09/Q06/R03 release-membership regression: interrupt a ready-set transition before and after fencing the timestamp group's release revision, then retry each phase. The new ready view cannot publish before that fence. Old copy evidence must fail after it, and an idempotent retry cannot substitute another worker set. Test bounded ACK pages across multiple pages, omissions, duplicates, stale enrollments, changed terminal/context digests, and actual worker transport provenance. Helper-only proof tests do not establish the service or transition assertions.

O13/O14/Q06 terminal-retirement regression: complete and expire enough requests to exceed the RAM queue's historical-identity capacity, then admit new valid work. Retire RAM records only after an authoritative non-executable terminal identity/digest tombstone or another proved retention protocol preserves delayed retry and receipt semantics. No pending request body, query or authorization payload enters durable storage. Query result expiry remains explicit, and a delayed mutation UUID cannot execute again.

O13/O15/Q02/R04 raw-resubmit regression: accept a mutation but stop all queue holders before Prepare, start an explicitly authorized new run, and deliver the original raw UUID/body again without a receipt run token. It must remain abandoned rather than become new-run work. The unchanged submit protocol requires a durable metadata-only UUID/digest/original-run reservation before acceptance. Test a lost reservation reply, API loss before 202, same-run admission retry, a conflicting digest, a fresh UUID after cold start and an old committed identity whose exact decision remains recoverable. Inspect decoded durable records to exclude request/query/authentication bodies, queue order and executable work. A reservation alone must never reconstruct a request. Bound RAM caches independently of the permanent identity history and reject unavailable identity storage before acceptance.

O05/O23/C02 native-open regression: inspect the pinned dependency's option sanitization and observe native threads after opening several pools, with the minimum and a larger configured background budget. Database open must not silently increase HIGH/LOW execution pools beyond the advertised maintenance budget. Reject an impossible configuration before creating/opening storage. Count query, control and maintenance execution capacity accurately; separately bound and charge housekeeping timers, network threads and their metadata/stacks. Record OS-specific observation limits rather than claiming a total-process bound from Rust executor thread IDs.

O13/M03 retained-reply regression: hold part of a reply arena, enqueue a reply requiring its full capacity, and repeatedly complete smaller fitting replies. Use deterministic release/dispatch barriers. Smaller work may bypass temporarily, but bounded aging must eventually protect enough headroom for the large eligible reply. No waiter holds CPU or a physical executor slot. Test cancellation and close without leaked reservations, and keep independent control replies progressing. General scheduler aging tests alone do not establish this separate allocator's fairness.

## Mapping to existing requirements

| Scheduler IDs | OLTP evidence |
| --- | --- |
| C01-C07, M01-M03, F01-F03 | O05/O13/O22/O26-O28 retain the shared assertions and extend them to data locality, multi-pool native overhead and bounded metadata/data traversal. |
| Q01-Q06 | O10/O13/O14/O23 preserve admission, replay/conflict rules, receipt retention, original authorization and all-ready RAM replication. Include every receipt/control regression named in the shared contract. |
| R01-R06 | O06/O10/O14-O16 retain same-run recovery, fences, final queue-holder behavior and cold-start abandonment. Any within-node abort isolation claim requires a tested process boundary. |
| T01-T06 | Preserve exact OLAP upload/CAS cases. O07-O11/O15/O21 separately test OLTP private preparation, one durable decision, ambiguity, fence ordering, limits and operation replay. These are analogous observations with a different publication mechanism. |
| U01-U03 | O01/O13-O15/O22 run local and distributed topology parity, bounded malformed input and generated event histories. |
| A01-A02 | O17/O18/O27 require the actual configured stateful adapter, safe pool/worker growth and migration/drain, and provider failure behavior. |
| B01-B02 | O23-O25 retain environment, utilization, queue/completion distributions, identity conservation and repeatability rules. |

All tests need bounded watchdogs and owned-process/task cleanup. Disk-fault fixtures need an actual durability model, not a memory-store acknowledgment that pretends to sync. Use deterministic event histories for no-torn-batch, stale-epoch and allocator-fence regressions; use actual EBS/EKS deployments for claims about AWS failure domains and lifecycle behavior. Retain failing seeds and minimal histories as regressions.

Future evidence belongs in `docs/testing/oltp-evidence.md` and task-specific data under `docs/testing/evidence/oltp/`. Record commit, engine features, toolchain/native versions, kernel/filesystem, instance/volume/region/AZ configuration, clocks/fault model, exact commands, seeds, assertions, observations, failures and cleanup. Distinguish planned cases, locally executed assertions and provider-executed assertions. No case in this document has been executed by the planning change.
