Our policy follows [T3 Code's contribution policy](https://github.com/pingdotgg/t3code/blob/main/CONTRIBUTING.md),
adapted for this repository.

## Scope

Outside contributions should fix bugs users can reproduce, including crashes,
regressions and measured performance problems. Features, new language clients,
storage providers, authentication methods and architectural changes need a
maintainer request before a PR. Link that request. Small obvious fixes need no
issue; larger fixes should link a bug report.

Search existing issues and PRs first. Test an existing fix instead of opening a
duplicate. Report bugs in [issues](https://github.com/nabedra/database/issues).
Propose features there for discussion before implementing them.

## Pull requests

Fix one problem per PR, including its necessary server, client, test and doc
changes. Explain the reproduction, verification commands and observed results.
Include before/after media for visual changes and name AI models that wrote code.
Following T3 Code, code from Gemini or Muse Wonder is not accepted; Muse Wonder
Full and reviews by those models are allowed.

Keep at most three PRs open and resolve conflicts within seven days. Review and
merge are discretionary. Avoid automated spam, repeated pings and attempts to
bypass limits. If a PR closes, address its reason and request reconsideration
there or link a focused replacement.

For changes to shared ORM behavior, including server changes that affect ORM
callers, update the Python and TypeScript implementations and tests in the same
PR. Compare public behavior with the same fixtures and server version. Bump both
package versions together, including for language-specific releases. Document
any language-specific exceptions and report skipped checks as unverified. [ORM parity policy](https://github.com/nabedra/database/blob/8ce51c071f2781b425544b6b45b4d2b73fc1a158/docs/testing/orm-parity.md)

## Development checks

Start in the root of the `nabedra-database` checkout. Keep build outputs,
credentials, local installations and generated acceptance reports out of
commits. [Server setup](https://github.com/nabedra/database/blob/8ce51c071f2781b425544b6b45b4d2b73fc1a158/server/README.md), [Python ORM setup](https://github.com/nabedra/database/blob/8ce51c071f2781b425544b6b45b4d2b73fc1a158/orm/python/README.md)

### Python

Use Python 3.11 or newer and install the checkout with the gateway extra.
Substitute your Python executable for `python3.11` if needed.

```sh
python3.11 -m venv orm/python/.venv
orm/python/.venv/bin/python -m pip install -e './orm/python[gateway]'
orm/python/.venv/bin/python -m unittest discover -s orm/python/tests -v
orm/python/.venv/bin/python -m unittest discover -s scripts -p 'test_*.py' -v
```

### TypeScript

Use Node.js 22.13 or newer. Install OpenSSL to enable the local TLS checks. The
test script compiles the package and checks types and runtime behavior.

```sh
(
  cd orm/typescript &&
    npm ci &&
    npm test
)
```

To enable the Python comparisons, set `NABEDRA_TEST_PYTHON` to an absolute path
to a Python 3.11 or newer executable. For live tests, set
`NABEDRA_TEST_SERVER_BINARY` to an absolute path to an OLTP build and
`NABEDRA_TEST_OLAP_BINARY` to an absolute path to a streaming-capable OLAP
build. Keep the two binaries at different paths, for example by setting a
separate `CARGO_TARGET_DIR` for each build. The live OLAP tests also need
`NABEDRA_TEST_PYTHON`. The suite skips comparisons and live checks whose paths
are unset. [TypeScript ORM verification](https://github.com/nabedra/database/blob/8ce51c071f2781b425544b6b45b4d2b73fc1a158/docs/testing/typescript-orm.md)

### Cache client contract

With Python 3.11 or newer, Node.js 22.13 or newer, and OpenSSL, run the shared
checks against both installed packages.

```sh
bash orm/cache-contract/run.sh
```

If `python3` is older than 3.11, set `NABEDRA_TEST_PYTHON` to a supported
executable. The runner creates a local protocol fixture and prints a pass for
each installed client. To also check server-backed behavior, point it at a
disposable Cache endpoint with `NABEDRA_CACHE_TEST_CONFIG`. This check sets
and deletes keys in the `catalog` namespace. [Cache test configuration](https://github.com/nabedra/database/blob/8ce51c071f2781b425544b6b45b4d2b73fc1a158/orm/cache-contract/README.md#check-both-installed-packages)

### Rust

Run these checks sequentially.

```sh
export CARGO_BUILD_JOBS=2 CARGO_PROFILE_DEV_DEBUG=0 CARGO_PROFILE_TEST_DEBUG=0
cargo fmt --manifest-path server/Cargo.toml --all -- --check
cargo clippy --locked --manifest-path server/Cargo.toml --all-targets -- -D warnings
cargo test --locked --manifest-path server/Cargo.toml
```

These commands use the default OLAP features. For OLTP, add
`--no-default-features --features oltp` to Clippy and tests. Place feature flags
before `--` in the Clippy command. For the full Cache test suite, run
`cargo test` on Linux with `--no-default-features --features cache`.
Check each affected engine when changing shared code.

Changes to worker execution or recovery must follow [AGENTS.md](https://github.com/nabedra/database/blob/1418bad88e1df1b8c868b88889a120e37059c1c0/AGENTS.md),
the [scheduling plan](https://github.com/nabedra/database/blob/1418bad88e1df1b8c868b88889a120e37059c1c0/plans/resource-aware-scheduling.md) and the
[scheduler test contract](/contributing/scheduler-contract). Cite scenario IDs
in test evidence, distinguish executed checks from untested behavior, and add
regression cases for new failures.

Shared test contracts and historical evidence stay in `docs/testing/`. Put
component setup and API documentation beside the component. The root README
should remain a repository map.
